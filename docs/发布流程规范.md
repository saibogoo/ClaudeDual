# 发布流程规范

本文件定义 ClaudexDual 的打包与发布流程。**任何人（包括 AI 助手）执行发布时都必须遵守本规范。**

---

## 一、三条铁律

### 1. 版本号由维护者指定，不得自行决定

AI **不得**自行推断版本号。即使按 semver 惯例判断"这应该是 minor"，也必须使用维护者指定的号。
维护者未指定时，**先询问**，不要默认。

### 2. 发布是公开动作，必须获得明确授权

推送 tag 会触发 CI 并**公开发布 Release**。只有维护者明确说了"发版 / 发布 vX.Y.Z"才可以执行。

- 「实现某功能」≠ 授权发布
- 「提交」≠ 授权发布
- 完成功能后应停下来问，不要顺手发版

### 3. 所有发布产物由 CI 生成，禁止手动上传

DMG、SHA-256、`latest.json` 全部由 GitHub Actions 生成。
**不要**在本地打包后手动上传到 Release——手动产物与 CI 产物可能不一致，且容易漏掉校验文件。

---

## 二、发布前检查清单

按顺序逐项确认，任何一项不通过就停止：

```bash
# 1. 工作区干净、分支正确
git status --short          # 应为空
git branch --show-current   # 应为 main

# 2. 提交身份正确（历史中不应出现其他邮箱）
git config user.email       # 应为 benhot.lee@gmail.com

# 3. 无密钥泄露（改动中不应出现真实密钥或个人路径）
git diff | grep -iEn 'sk-[a-zA-Z0-9]{15,}|/Users/[a-zA-Z]+'

# 4. 本地构建通过（CI 会跑同样的检查，先在本地拦下问题）
UNIVERSAL=1 tools/PackageApp.sh
python3 -m unittest discover -s tests
```

---

## 三、发布步骤

### 第 1 步：更新 CHANGELOG.md

在文件顶部（`# 更新日志` 与说明之后）新增版本段落：

```markdown
## v1.3.1

- 面向用户描述本次变更，一条一行
- 用用户能看懂的话，不要写内部实现细节
```

**格式要求（CI 依赖，写错会导致发布失败）：**

- 标题必须是 `## v` + 版本号，与 tag 完全一致（`## v1.3.1` 对应 tag `v1.3.1`）
- 段落内容会被自动提取，作为**应用内升级弹窗**显示的更新说明
- 弹窗是纯文本渲染，**不要用表格、多级标题或复杂 Markdown**，用 `-` 列表即可
- 若有需要用户手动处理的事项（如需删除旧应用），必须在此写明

### 第 2 步：同步版本号

```bash
/usr/libexec/PlistBuddy \
  -c "Set :CFBundleShortVersionString 1.3.1" \
  -c "Set :CFBundleVersion 8" \
  -c "Set :ClaudeDualReleaseTime $(date '+%Y-%m-%d CST')" \
  Resources/Info.plist
```

- `CFBundleShortVersionString` **必须**等于 tag 去掉 `v`，否则 CI 的版本校验会失败
- `CFBundleVersion`（build 号）每次发布递增
- `ClaudeDualReleaseTime` 更新为当天日期

### 第 3 步：本地验证

```bash
UNIVERSAL=1 tools/PackageApp.sh
python3 -m unittest discover -s tests
/usr/libexec/PlistBuddy -c "Print :CFBundleShortVersionString" ClaudexDual.app/Contents/Info.plist
```

确认：编译零错误、测试通过、产物版本号正确、架构为 `x86_64 arm64`。

### 第 4 步：提交并推送

```bash
git add CHANGELOG.md Resources/Info.plist
git commit -m "release: v1.3.1 — 一句话说明

Bump version to 1.3.1 (build 8)."
git push origin main
```

### 第 5 步：打 tag 触发发布

```bash
git tag -a v1.3.1 -m "ClaudexDual v1.3.1"
git push origin v1.3.1
```

推送 tag 后 CI 自动执行全部发布工作，**无需任何手动操作**。

### 第 6 步：验证发布结果

等 CI 完成（约 1 分钟）后确认：

```bash
# Release 应包含三个文件：.dmg、.dmg.sha256、latest.json
# latest.json 的 notes 应为 CHANGELOG 中的真实内容
curl -sL "https://github.com/saibogoo/ClaudeDual/releases/latest/download/latest.json"
```

检查项：
- [ ] `version` 与本次发布一致
- [ ] `notes` 是真实更新内容（不是占位文字）
- [ ] `asset.url` 路径以 `/saibogoo/ClaudeDual/releases/download/` 开头（**在线升级的白名单前缀，不匹配则所有老用户升级失败**）

## 四、绝对不能改的标识

以下标识与**已安装用户的数据和升级链路**绑定。产品叫 ClaudexDual，但这些**必须保持 ClaudeDual 原样**：

| 标识 | 值 | 改动后果 |
|------|-----|---------|
| Claude 数据目录 | `~/Library/Application Support/ClaudeDual-3p` | 用户配置和登录态"消失" |
| Codex 数据目录 | `~/Library/Application Support/ClaudeDual/CodexInstances/` | 同上 |
| 钥匙串 service 前缀 | `ClaudeDual.Codex.` | API 密钥读不出来 |
| Bundle ID | `com.local.ClaudeDual` | 被视为新应用 |
| Info.plist 自定义键 | `ClaudeDualReleaseTime` | 关于页读不到发布时间 |
| 旧 UserDefaults 域 | `com.local.ClaudeDual` 等 | 旧配置无法迁移 |
| GitHub 仓库 URL | `saibogoo/ClaudeDual` | **在线升级白名单校验失败，全部老用户升不了级** |
| Codex provider id | `claudedual_<uuid>` | 生成的 Codex 配置失效 |

> 改名、重构时若要做全局替换，**必须先保护上述模式**再替换。
> 注意路径可能带转义空格（`Application\ Support/ClaudeDual-3p`），简单前缀匹配会漏掉。

## 五、CI 做了什么

`.github/workflows/release.yml` 在收到 `v*` tag 后依次执行：

1. 校验 tag 格式为 `vMAJOR.MINOR.PATCH`
2. 检出该 tag
3. **校验 `Info.plist` 版本与 tag 一致**（不一致则失败）
4. 运行代理回归测试
5. 构建通用二进制（arm64 + x86_64）并 ad-hoc 签名
6. 打包 DMG（含应用、Applications 快捷方式、安装说明），生成 SHA-256
7. **从 `CHANGELOG.md` 提取对应版本段落**生成 `latest.json`（缺段落则失败）
8. 创建 Release 并上传三个文件

## 六、常见问题

**推送报 `the remote end hung up unexpectedly`**
提交含较大二进制时 HTTP 缓冲不足：

```bash
git config http.postBuffer 524288000
```

**CI 报 `CHANGELOG.md has no section for vX.Y.Z`**
CHANGELOG 缺少对应版本段落，或标题与 tag 不完全一致。补上后重新打 tag。

**CI 报 `Resources/Info.plist is X but release tag is vY`**
忘了同步版本号。修正 `Info.plist`、提交、删除旧 tag 后重新打。

**升级弹窗显示占位文字**
`latest.json` 的 `notes` 没取到真实内容。检查 CHANGELOG 段落格式，必要时可修正后重新生成并替换该 Release 的 `latest.json`。

**推送 workflow 文件被拒（缺 `workflow` scope）**
凭证权限不足。确认 token 具备 `workflow` scope：

```bash
curl -s -I -H "Authorization: token $TOKEN" https://api.github.com/user | grep -i x-oauth-scopes
```

## 七、发布后

- 如需更详细的 Release 页面说明（安装步骤、升级提示、校验命令），可在发布后补充 Release 正文；
  但**应用内弹窗只读 `latest.json` 的 notes**，面向用户的关键信息必须写在 CHANGELOG 里。
- 涉及跨版本行为变化（如应用改名、需手动删除旧版）时，必须在 CHANGELOG 中明确写出用户要做的操作。
